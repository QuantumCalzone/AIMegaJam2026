### What was built

1. **Banners (`WBP_Stage.ShowBanner`).** It prints `NHOS: BANNER`, clears the `FadeBanner` timer (that one timer is both the 3.5 s hold and each 0.05 s fade step), empties `BannerQueue`, adds the new line and calls `NextBanner`, which shows it at full opacity and starts its 3.5 s hold. `NextBanner` and `FadeBanner` didn't change. `BannerQueue` now holds at most one line; it stays, so `NextBanner`'s form is unchanged for T34. `ShowSceneBanner` (Scene Prep) calls `ShowBanner` directly and replaces in the same way.
2. **The Back mark (`BP_StageDirector.PickSpot`, new `FindCam`, new variables `CamPos` and `MinGap`).**
   - **Why it happened:** the Back mark's first spot is (220, 0), 220 cm straight behind the middle home spot (0, 0). T19's rule counts a spot as taken only within 140 cm in depth, so (220, 0) was free whenever its lane was empty in depth. The camera (`CameraActor` at (-1050, 0, 330), pitch -20) sees a robot there over the home-row robot's shoulders only from about 2 m up: the ray to its feet crosses the home row 57 cm up, and the ray to a 170 cm head crosses it at about 198 cm, so the robot in front covers all but the head and the label. The level's marks were read with MCP (`BP_PlaceMark` `Spots` plus each actor's location); the robots' homes are (0, 0), (-12, ±165) and (-50, ±330).
   - **The fix (no level change):** `PickSpot` keeps T19's crowding rule (95 cm sideways and 140 cm in depth) and adds a line-of-sight rule. For each candidate spot and each other robot's goal it takes the sideways offset over the distance from the camera, (y - cam.y) / (x - cam.x), the tangent of the angle each makes with the camera's view, which looks down +X. If any two differ by less than 0.06 (about 63 cm at the home row), the spot is taken. `FindCam` reads the level's `CameraActor` each time, with (-1050, 0, 330) as the fallback, so the rule follows the camera if T106 moves it. A picked spot prints `NHOS: SPOT x= y= gap=` with the smallest gap.
   - **What it does to the marks, with every other robot at home:** Back's (220, 0) is taken (behind the middle home) and its back-row spots at x = 80 too; (220, ±110) are free, with a gap of 0.072 to the nearest home and 0.087 to the middle. A robot that leaves its home frees its lane, so most moves still find a spot. Front's (−190, 0) and (−190, ±115) are now taken, because a robot there would hide the home robot behind it. A move that finds no spot turns into a look at the place, as T19 made it (`NHOS: ACT <id> look Back - (no free spot)`, once in the PIE show, when OpenAI tried Back with both free Back spots taken).
3. **`fast_lines`.** The switches' `_readme` (in `Docs/switches.example.json` and this Mac's `Local/switches.json`) now says it is read once, when the game queues its first line or cue after it starts (`BPC_LinePlayer.LoadPacing`, behind `Loaded`, which `Clear` doesn't reset), so Play Again doesn't read it again and a change waits for a new PIE session or game window. The general sentence now says the switches are read at each scene and each Cut "except where a switch below says when it is read". `LoadPacing` didn't change.
4. **Free mode's repeats (`BPC_LLMClient.FreePickLine`, new; `FreeReply`).** `FreePickLine` picks an index into `TmpArr2` that is none of the last `FreeK` picks of the same phase, `FreeK = min(count - 1, 3)`, from `FreeRecent` (`<phase id>#<index>` per pick, newest last, at most 40). A round has at most four AI speakers, so any four picks in a row of one phase differ while the phase has four or more lines. `FreeReply` calls it for a phase's `lines` and, after the PIE show's vote gave two seats the same reason, for a vote's or closing's `reasons` too (the tell uses the same index, as before). Each pick prints `NHOS: FREE LINE phase= idx=`. `free_mode.json` and the relay's free mode didn't change: the relay answers one request at a time and keeps no rounds.
5. **The DSL check (`Tools/check_graphs.py`, new; `check_prompts.py`).** It parses each `Graphs/**/*.txt` (comments dropped, strings and `(:"Label")` kept whole) and fails an `if` whose own body ends in a branching node (`Utilities|IsValid`, or any node with a `(:"...")` child), directly or through a nested `if` that ends the body, when code follows it in the same body or after an `if` or a branch that holds it. The end of a `for` body goes back to the loop, so code after a `for` doesn't count. `check_prompts.py` runs it after the sample-show checks, so `--offline` (and every other mode) fails on it. The plan's build notes have the rule ("The DSL's else trap").
