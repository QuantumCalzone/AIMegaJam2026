# T32 UI/UX audit, style guide and shared pieces

Back to [the plan](../Plan.md). This task's title line, **Model and effort**, **Depends on**, **Needs**, **Touches** and any **Waiting:** or **Blocked:** line are in its entry there, under "Open".

## Task

- **Why:** my playtests keep finding text that is hard to read and screens that look unfinished (T14, T27), and visuals is a judging criterion. This task checks the whole UI the way a senior game UI/UX designer would. T34 and T33 fix what it finds.
- **Steps:**
  1. **Decide before you change.** Start from the Screens table in the doc's UI direction. For each screen below, write the one thing I must see and the one thing I must do next, and rank everything else (primary, secondary, tertiary). Size, weight, color and position follow the rank. Look at one or two comparable chat-heavy party games for what readable looks like.
     The screens: title, key entry, Scene Prep, a scene turn (mine and the AIs'), Free Talk, the vote (before and after a pick), the reveal stamp, a cut, the last reactions with "See the results", the win and lose end screens, the money burn (T35) over a scene turn, and the unavailable screen T21 adds, if T21 is done.
  2. **Screenshot every screen and state** at 1600 × 900 and 1280 × 720, with the methods that "T27: the screen floats over the stage" in [T27.md](T27.md) lists (PIE by hand through the Slate inspector for the phases, a game window for the real look). Test the worst cases: the longest provider name, a long AI line, a full cast of five. Save them in `Saved/T32/shots/` (not in git).
  3. **Audit against known rules, and name the rule for each problem:** visual hierarchy, contrast (WCAG), a type scale, a spacing grid, alignment, consistent components, clear states and feedback (Nielsen's heuristics), safe margins from the window edge, and no meaning carried by color alone. Write the result under "T32: UI audit" in this file's "## Findings", as a table: for each screen its primary focus and next action, then each problem with its rule, ranked by how much it hurts a player, with the fix and the task that does it (T32, T34 or T33).
  4. **The design system is the doc's UI direction:** the UI section under "Art direction" on the design doc's Art Inspiration tab (`Docs/UIStyle.md` links it). It sets the palette by role, the type scale, the components and their states, each screen's focus and next action, and the motion times. Don't restate it in a file. Where the audit needs a value the doc lacks (for example the spacing steps or a state color), show me the edit to the doc, and make it after my OK. Record any new font or art in `Docs/Assets.md`.
  5. **Put each value in one place.** A new Blueprint (for example `UIStyle`) holds the doc's palette, sizes and spacing, and the widgets read them from it. Build the shared pieces with it: the button styles for every state (as a function the widgets call), and `WBP_ChatLine`. The rest of `WBP_Stage` is T34's, and the other widgets are T33's.
  6. **A cold review.** A subagent reads the screenshots and the table, without your reasoning, and critiques them as a design reviewer. Add what it finds that the table lacks.
- **Done when:** the table covers every screen in the list, and every problem in it has a fix and a task; the style Blueprint holds the doc's UI values; screenshots show all four button states in the shared styles; a free autoplay show reaches `NHOS: SHOW END` with no new `LogScript` warning and its `NHOS: LOG` lines in the same form; I read the table and any doc edits and say go.
