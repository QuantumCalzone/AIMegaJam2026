# T89 Post-jam builds go to itch.io with butler on every push

## Task

- **Why:** my request on 2026-11-15: when `noHumansOnSet` changes, a new build should go to the game's itch.io page, https://quantumcalzone.itch.io/no-humans-on-set, with no one packaging or uploading it by hand. butler (https://itch.io/docs/butler/) is itch.io's command-line uploader. It pushes a folder to a "channel", and each channel is one file on the page. A later push to the same channel replaces that file and uploads only what changed. ("The main branch" in my request means `noHumansOnSet`, this repo's main branch; see CLAUDE.md.)
- **The jam's file must not change.** The jam closed on 2026-11-15, and judges play the file we submitted. Never replace, rename, hide or delete it, and keep it first on the page. Every build that this task makes goes to a new channel as a second file, clearly marked post-jam. My memory note on the jam has the reasons.
- **Every post-jam download says it is post-jam** (my word on 2026-11-15). The file a player downloads, its label on the page and the folder inside the download all say "PostJam". The same holds for any zip we make by hand after the jam, Windows or Mac.
- **What butler's docs don't say.** They don't say what name a pushed channel's file gets on the page, or what file name a player's browser saves, and butler has no flag that sets either. So this task finds out with a hidden first push (`--hidden` works only on a new channel). Then it fixes the names and records how it did that.
- **Why a self-hosted runner.** GitHub's own runners have no Unreal Engine, and packaging also needs Visual Studio 2022 and the Windows 11 SDK. This PC has them all and has packaged the game before. So the build runs on this PC as a GitHub Actions self-hosted runner. Self-hosted runner minutes cost nothing.
- **Steps:**
  1. **Read first.** Read butler's pages on pushing, logging in and installing, and GitHub's docs on self-hosted runners. Read "Package a Windows build" and the secrets check in CLAUDE.md. A short search should settle what butler's docs leave open (see "What butler's docs don't say"). Check whether the repo is public. Either way, the workflow runs only on `push` and `workflow_dispatch`, never on `pull_request`, because a fork's pull request could run code on this PC.
  2. **Install butler.** Ask my OK first, then download it from broth: `https://broth.itch.zone/butler/windows-amd64/LATEST/archive/default`. Check the channel name on broth. Then I run `butler login` myself. It stores my key in `%USERPROFILE%/.config/itch/butler_creds`, outside the repo. The key never goes in git or in chat.
  3. **The script: `Tools/deploy_itch.py`** (Python 3.10+, no packages, so the Mac can use it later). It does every step from a clean commit to a push, and the workflow only calls it:
     - Package the commit with the "Package a Windows build" command, into a new folder per run (for example `Packaged/deploy/<short sha>/`). Write the command to a `.bat` and run it with `cmd /c`, as CLAUDE.md says.
     - Name the build's top folder `NoHumansOnSet_PostJam_Windows`, so the post-jam name is also inside the download.
     - Delete every `.pdb`, and any `Local/` or `Saved/` folder in the build.
     - Run `Tools/check_build_secrets.py` on the build. Push nothing unless its exit code is 0. An exit code of 2 (part not checked) also stops the push.
     - Push with `butler push <build> quantumcalzone/no-humans-on-set:windows-postjam --userversion postjam-<YYYY-MM-DD>-<short sha> --if-changed`. The word "windows" in the channel tags the file as Windows.
     - Flags: `--dry-run` (everything but the push), `--hidden` (the first push only), `--build <folder>` (push a build that is already made), `--commit <sha>`.

  4. **The secrets check outside the repo folder.** `check_build_secrets.py` finds our keys in `Local/` next to its own `Tools/` folder. A build checkout has no `Local/`. Give the script a `--local <folder>` option, and have the deploy script pass the repo folder's `Local/`. Without our keys, the check looks only for key shapes, so the deploy script must stop if the check prints that it found no key files.

Each run first stops any such process whose command line names the deploy worktree, then `git reset --hard`, `git clean -fd` (ignored folders such as `DerivedDataCache/`, `Intermediate/` and `Saved/` stay, so later cooks are faster), `git checkout --detach --force <sha>` and `git lfs pull`.
