# T37 Error messages say what went wrong, with a joke

Back to [the plan](../Plan.md). This task's title line, **Model and effort**, **Depends on**, **Needs**, **Touches** and any **Waiting:** or **Blocked:** line are in its entry there, under "Open".

## Task

- **Why:** my request on 2026-11-15. Error messages should be funny but still tell me what actually went wrong. For example, when a key runs out of credits, the game can joke that the key's owner is cheap. Today the screens use flat text, and a robot whose reply failed just looks around: an out-of-credits key, a rate limit or a lab at capacity looks the same as a robot with nothing to say. The design doc's tone is "playful, petty slapstick" (Art Inspiration), and its Tech & Build tab now asks for this rule.
- **Where error text comes from today** (found on 2026-11-15, all in `BPC_LLMClient`):
  - Before a relay show, `OnHealth` sets one of 4 fixed messages for the unavailable screen.
  - During a relay show, `HandleHttp` calls `GoDown` with the relay's own `error.message` (`MESSAGES` in `Relay/src/index.js`), or with a fixed line when the relay stops answering.
  - On the key screen, `OnKeyTest`, `KeyTestResult` and `SetMode` write the notes ("Anthropic: the key didn't work (authentication_error).").
  - During any show, a reply that fails after its one retry goes to `Deliver` with `Ok` false. `BP_Show` then makes the robot look around (a scene turn), pass (Free Talk) or stay silent (a reaction), and I'm told nothing. Through the relay, any failure at the lab (for example xAI at capacity) comes back as `provider_error` with the lab's HTTP status in `upstream_status`, and ends the same way.
- **Steps:**
  1. **The lines go in a data file,** new `Content/NHOS/Data/errors.json`: one entry per case in "Approved lines" below, each a list of 2 lines, and the game picks one at random. Fill in `{lab}` (the provider's display name from `personas.json`: OpenAI, Anthropic, SpaceXAI or Meta), `{n}` and `{type}`. Every line says what happened in its first sentence, then makes the joke. Keep each approved line as it is and write a second one for each case in the same voice. Add a `_readme`. Add an `--offline` check of the file to `Tools/check_prompts.py`: every case has a line, no unknown placeholder, and no line uses a persona name.
  2. **Sort each failure into a case,** with a new function, `BPC_LLMClient.ErrorKind`. It reads `ErrType` and `ErrMsg` (the error's `type` and `message`, which `ParseReply` already keeps), the relay's `upstream_status` (make `ParseReply` keep it too) and the reason that `HandleHttp` builds (`transport ...`, `finish_reason ...`, `stop_reason ...`, `refusal ...`, `reply is not JSON: ...`). Check in this order:
     - `transport`: **no reply**.
     - The relay's own types (`session_limit`, `player_limit`, `budget_used_up`, `provider_unavailable`): each is its own case.
     - **Out of credits:** type `insufficient_quota` or `billing_error`, or the message has "credit", "quota", "billing", "balance" or "spending limit".
     - **Rate limited:** type `rate_limit_error`, `rate_limit_exceeded`, `requests` or `tokens`, or the message has "rate limit" or "too many requests". Through the relay, `upstream_status` 429 is **relay 429**, because the relay can't tell a rate limit from our spending cap.
     - **Overloaded:** type `overloaded_error`, or "overloaded", "capacity" or "high demand" in the message, or `upstream_status` 503 or 529.
     - **Key rejected:** type `authentication_error`, `permission_error` or `invalid_api_key`, or "api key" in the message.
     - **Cut off:** `finish_reason length`, `stop_reason max_tokens`. **Refused:** a refusal, `content_filter`.
     - **Can't be read:** not JSON, or no text, with no keyword above. A plain-text reply goes through the keyword checks first, so xAI's "The model is currently at capacity ..." lands on **overloaded**.
     - Any other relay `provider_error`: **relay provider**. Anything else: **unknown**.
     - The provider's message is read only for these keywords and never shown, because some providers echo part of the key (T21).
  3. **One function makes the text,** `ErrorLine(Kind, Lab, N, Type)`, and every place that writes error text today uses it: `OnHealth`, both `GoDown` calls in `HandleHttp`, `OnKeyTest`, `KeyTestResult` and `SetMode`. For a relay type that `errors.json` has no line for, the relay's own `error.message` stays the fallback. Key-test notes keep the lab and the error type in parentheses, never the provider's text. Print `NHOS: ERROR <kind> provider=<id> where=<health|down|keytest|turn>` each time.
  4. **A backstage note during the show.** When an actor's reply fails after its retry, the client passes `BP_Show` the line, and one node in `BP_Show` shows it on T29's banner (`EventBanner`), long enough to read (about 6 s; T30's line queue decides when it shows). The robot still looks around, passes or stays silent as now. Show at most one note per lab per scene, so a lab that keeps failing doesn't fill the show.
     - The note is for my screen only. It never goes in the shared log the AIs read (the build notes keep errors out of it, and the note names the lab, which the AIs must never see) or in `game_messages`.
  5. **A test switch, so the checks cost nothing.** `"error_test": "<case>"` in `Local/switches.json` makes Test for Free fail one actor ask per turn with a canned reply body for that case, sent through the real `ParseReply`, `ErrorKind` and `ErrorLine`. Make each body realistic: OpenAI's `insufficient_quota` JSON, Anthropic's credit-balance and `overloaded_error` JSON, xAI's plain-text "at capacity" reply, a `finish_reason: length` reply, and so on. Add the switch to `Docs/switches.example.json`.
  6. Don't change the relay. Its `MESSAGES` stay as they are.
- **Done when:**
  - Free autoplay shows with `error_test` set to each of out of credits, rate limited, overloaded (the plain-text body), key rejected, no reply, cut off, refused and can't be read: each prints its `NHOS: ERROR <kind> ... where=turn` line and reaches `NHOS: SHOW END`, and no `NHOS: LOG` line (the shared log) holds note text. A screenshot shows one note on the banner.
  - With a wrong relay address, the unavailable screen shows the relay-down line. With T21's local stub relay (every ask `budget_used_up`), it shows the budget line mid-show. Screenshots of both.
  - On the key screen, **Test keys** with no keys, **Save and Play** with 2 keys, and **Test keys** with a fake Anthropic key (one real call, which costs nothing) show their lines with no provider text. Screenshots.
  - `python Tools/check_prompts.py --offline` passes.
  - Screenshots at 1600 × 900 and 1280 × 720 show no clipped text on the banner, the unavailable screen or the key screen.

## Approved lines

I approved these first lines on 2026-11-15. `{lab}` is the provider's display name.

**The unavailable screen**

| Case | Line |
|---|---|
| Relay down (health) | "The AI relay isn't answering: it's down, or you're offline. The robots are standing in the dark, waiting for their cue." |
| Reply can't be read (health) | "The AI relay answered, but the game can't read the reply. Even the robots couldn't make sense of it." |
| Daily budget gone | "Today's free AI budget is used up (it resets at midnight UTC). Our producers are cheap and burned it all." |
| Fewer than 3 labs | "The relay can reach only {n} of the 4 AI labs, and a show needs 3. Half the cast called in sick." |
| Show limit | "This show has used all its free AI calls. The producers cut the budget mid-scene. Enter your own API keys to finish." |
| Player limit | "You've used all of today's free AI calls. That's a lot of improv. Enter your own keys, or come back tomorrow." |
| Lab not set up on the relay | "The relay has no key for {lab}, so {lab} can't go on. Someone forgot to sign its contract." |
| Relay dropped mid-show | "The AI relay stopped answering: it went down, or your connection dropped. The lights are on, but nobody's home." |

**Backstage notes during a show**

| Case | Line |
|---|---|
| Out of credits | "{lab}'s API key is out of credits, so it has no tokens left to think with. Whoever owns that key is cheap. (If it's yours: hi.)" |
| Rate limited | "{lab} hit its rate limit: too many requests, too fast. It's on a mandatory union break." |
| Overloaded | "{lab}'s servers are full right now, so its line never came. Everyone else is asking {lab} for things too." |
| Key rejected | "{lab} rejected its API key (wrong, expired or revoked). It won't perform without a valid contract." |
| No reply | "{lab} never answered: the request timed out or the connection dropped. It froze like it forgot its lines." |
| Cut off | "{lab}'s reply hit its length limit and got cut mid-sentence. It was going to be brilliant. Probably." |
| Refused | "{lab}'s safety filter refused this line. Very principled. Very method." |
| Can't be read | "{lab} answered, but in a shape the game can't read. It ad-libbed so hard it broke the script." |
| Relay 429 | "{lab} told the relay 'too many requests': it's rate limited, or our producers hit their spending cap." |
| Relay provider | "{lab} didn't answer through the relay; the problem is on {lab}'s end. It'll try again next turn." |
| Unknown | "{lab}'s request failed with an error the game doesn't recognize ({type}). It's improvising silence." |

**The key screen**

| Case | Line |

## Findings

- **What isn't known yet:** how SpaceXAI and Meta word an out-of-credits error. OpenAI uses the type `insufficient_quota`, and Anthropic says "credit balance" in the message. If a lab's wording matches no keyword, its error falls to **unknown**, which is still true. Through the relay, the lab's details are hidden, so relay errors can say "overloaded" or "rate limited or over the cap", never "out of credits".
