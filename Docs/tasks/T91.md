## Findings

Part 1 (2026-11-19, PC, before the first release):

- **My calls.** Asked how a release goes in, I first picked a pull request that I merge. Asked next for my OK on a ruleset for `main` (no force pushes, no deletion, a pull request, merge commits only, no bypass), I said: "Actually, we don't need that many rules. This is a game jam project. Just merge into main." So GitHub gets no branch rules and there is no pull request: an agent merges `dev` into `main` on my word. That answer was also my word for the first release.
- **A release is a fast-forward, made with a push alone:** `git fetch origin`, then `git push origin origin/dev:refs/heads/main`. No working tree changes (the repo folder stays on `dev`), and git refuses the push if `main` ever holds a commit that `dev` lacks, since nobody force-pushes. It also keeps `main` an ancestor of `dev` for every later release. The other way, a merge commit (`--no-ff`), marks each release in `main`'s history, but `main` is then never an ancestor of `dev` again, and making it without checking out `main` needs `git commit-tree`. With no pull request, the fast-forward is simpler. So the version on itch.io is the released `dev` commit's (Done-when 4's "merge commit" assumed a pull request).
- **`main` before the release:** `d9cde1a`, the first setup, an ancestor of `dev` and 513 commits behind it. It had no protection: GitHub's public API says `"protected": false` for the branch, and its rules for `main` are `[]`. The repo is public and owned by a user account. This PC has no `gh`.
- **The menu.** `Tools/deploy_itch.py`: the default commit is `origin/main`; it fetches `main` and `dev`; its output says whether the commit it builds is `main`'s tip, and a real push of any other commit prints a note that the build is not a release. `Content/Python/nhos_itch_deploy.py`: the upload dialog names `main` and says how to ship newer work; "Build only (dry run)" is now "Build only (dry run of main)"; a new entry, "Dry run of dev", passes `--commit origin/dev --dry-run`; `launch()` takes a `commit`. A check with a stand-in `unreal` module: `register()` adds the four entries in order and logs `NHOS: ITCH MENU added (Tools > itch.io, 4 entries)`; "Build only" starts `deploy_itch.py ... --dry-run`, and "Dry run of dev" starts `... --commit origin/dev --dry-run`, each through `cmd /c "... & pause"`. Part 2 (2026-11-19, PC, the first release):

- **Dry run of `dev` first.** The menu's "Dry run of dev" command, by hand (`deploy_itch.py --commit origin/dev --dry-run` with the menu's other arguments): it built `10f8540` in the deploy worktree, logged "not main's tip d9cde1a: not a release", deleted one `.pdb`, the secrets check was clean, and it saw the `windows` channel. Exit code 0.
- **The release:** `git push origin 10f8540:refs/heads/main`, after a check that `origin/main` was an ancestor of it (the exact commit the dry run built, not whatever `dev` was a moment later). `d9cde1a..10f8540`. The repo folder stayed on `dev`; its local `main` ref was moved along with `git branch -f main origin/main`.
- **The upload, and a bug it found.** The menu's upload command, by hand (no `--commit`): it built `10f8540` as "main's tip, the last release", the secrets check was clean, and butler started the push. Then the script died with a `UnicodeEncodeError`: it read butler's output in the Windows code page, butler's UTF-8 progress marks held bytes that cp1252 doesn't define, they became U+FFFD, and printing that to a redirected stdout (cp1252) failed. In the menu's console window Python writes to the console in UTF-8, so the menu may never have hit it, but the script must not depend on that. The fix: child output is read as UTF-8, `stdout` and `stderr` print with `errors="replace"`, and so do the butler status read and git.
- **butler finished the push anyway.** When the exception left the `with subprocess.Popen(...)` block, Python closed the pipe and waited for butler, which went on and finished: build #2443483 (from #2412502, 854 MiB of files, a patch on the last build). A second push of the same build with the fixed script (`--build <that build> --commit origin/main`) found "No changes and --if-changed used", which is right. The script still said "pushed", so it now says "nothing pushed: ... already has this build" when butler skips a push.
- **`--build` and `--commit`.** With `--build`, the version label used the commit only when `--commit` differed from the default, so `--commit origin/main` would have labelled the build `<date>-manual`. Now `--commit` has no default in argparse: with `--build`, any `--commit` given sets the label; without `--build`, no `--commit` means `origin/main`.
- **The page, signed out, in the browser pane:** one file, "no-humans-on-set-windows.zip 584 MB Version 2026-11-20-10f8540". `butler status`: `windows`, upload #20604160, build #2443483, `2026-11-20-10f8540`. No other channel. A plain `curl` of the page got itch's 429, so read it in a browser.
- **The version's date is UTC.** `10f8540` was committed on 2026-11-19 in local time, after midnight UTC, so its label says 2026-11-20.
