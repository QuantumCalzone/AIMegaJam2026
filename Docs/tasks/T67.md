## Task

- **Model and effort:** Sonnet 5.5, medium. A new route and store in a Worker that already has its checks and limits, plus a report script and curl tests.
- **Depends on:** nothing.
- **Needs:** no editor. My OK before the relay is deployed again (every push deploys it). A new `STATS_KEY` secret or a read-only Cloudflare API token for the report, which I set.
- **Touches:** `Relay/src/index.js`, `Relay/relay.config.json` (`events`, `limits.ip_daily_events`), `Relay/wrangler.toml` (the store's binding), `Relay/test/curl-tests.sh`, `Relay/README.md`, new `Tools/analytics_report.py`, new `Docs/stats.example.json`, `Docs/tasks/T67.md`.
- **Why:** I want to know how many people start the game, how many come back, which mode they play (free, relay or their own keys), where they stop, how many LLM calls go to which provider, and which actions they try that the game can't do. The relay only sees Play via Relay today: Test for Free makes no network call, and Play with my own API keys calls the providers directly. So the game must report for itself (T68, T69), and the relay we already run is the place to collect it. This task is the server half. It needs no editor.
- **Steps:**
  1. **Pick the store.** Either Workers Analytics Engine (built for event data: `writeDataPoint` never blocks, and it's queried with SQL over Cloudflare's API with a read-only API token), or a new SQLite Durable Object, `Stats`, read through a key-protected route. Check both on the current free Workers plan (writes per day, reads, storage, how long data is kept) and pick the one that holds judging week's data with the least setup. Never use the `Limiter`: it deletes everything at each new UTC day. Write the pick and why under "## Findings".
  2. **`POST /event`** in `Relay/src/index.js`, with `content-type: application/json` and this body: `{"player": <32 hex>, "session": <8 to 64 letters, digits, - or _>, "build": <up to 20 chars>, "mode": "free" | "relay" | "keys" | "", "event": <name>, "fields": {...}, "test": true | false}`.
     - The allowed events and their fields are an allow-list in `Relay/relay.config.json` (a new `events` block), each field with a type and a cap: a string's length, a number's range. Start with T68's and T69's events: `launch` (`launches`, `first_seen`), `mode`, `show_start`, `phase` (`phase`, `scene`), `show_end` (`result`, `reason`), `calls` (`provider`, `model`, `calls`, `failed`, `tokens_in`, `tokens_out`), `error` (`kind`), `unsupported` (`words`, `source`, `phase`), `analytics_off`.
     - Anything else is a `bad_request` in the relay's usual error shape: an unknown event, an extra field, a wrong type, a string over its cap.
     - Store the row with the UTC time and the relay's day-salted address hash (`hashIp`), never the address.
     - Answer `{"ok": true}`. It never calls a provider and never touches the call budget.
  3. **Limit it** so junk costs nothing: a new per-address daily count for events (`limits.ip_daily_events`, start at 500, about 20 shows), kept apart from the call counts, and a body cap far below the relay's (2 KB). A refused event answers `player_limit` like a call does.
  4. **Read it back.** If the store is a Durable Object, add `GET /stats` that needs `Authorization: Bearer <STATS_KEY>` (a new Worker secret, which I set) and answers 404 without it, as for any unknown path. Add a new `Tools/analytics_report.py` (Python 3.10+, no packages, like `check_prompts.py`). It reads its key or token from a new `Local/stats.json` (an example in `Docs/stats.example.json`; it never goes in `llm_key.json`, which ships next to the packaged game) and prints:
     - players: distinct player ids, and how many came back (`launches` over 1, or seen on two or more days)
     - modes: players and shows per mode
     - drop-off: shows that reached each phase, in show order, and the `show_end` results
     - calls: per provider and model, with failures and tokens in and out
     - errors: by kind
     - unsupported actions: the most common `words`
     It takes `--since <date>`, and it leaves out `test` events unless given `--test`.
  5. **Tests.** `Relay/test/curl-tests.sh` gets event tests: a good event is stored, each bad shape is refused, the event limit trips (lower it with a var, as the call limits do), `/stats` refuses a missing or wrong key, and a `test` event shows only with `--test`. The existing 23 tests still pass.
  6. **Docs.** `Relay/README.md` gets a section on `/event`, the store, the limits and how to read the report. It also says what is stored: an anonymous player id, the mode, the phases, call counts and tokens, error kinds and a few words for an unsupported action. Never typed text, keys or the address.

## Findings

### The store: a SQLite Durable Object, `Stats` (step 1)

Both were checked against Cloudflare's docs for the free Workers plan on 2026-11-15:

| | Workers Analytics Engine | SQLite Durable Object |
|---|---|---|
| Writes | 100,000 data points a day | 100,000 rows written a day (an event is about 2: the row and the address's count) |
| Reads | 10,000 SQL API queries a day | 5 million rows read a day |
| Storage, kept for | 3 months, then dropped | 5 GB for the account, kept until deleted |
| Setup to read it | an account ID and a Cloudflare API token with Account Analytics Read, both in `Local/stats.json` | one Worker secret, `STATS_KEY`, and the same key in `Local/stats.json` |
| Testing | writes do nothing under `wrangler dev`, so only the live relay can be tested | the whole route, store, limit and report run under `wrangler dev` |
| Cost now | Cloudflare doesn't bill it yet and says billing will start later | inside the free plan's allowance; the relay's `Limiter` is already one |

Picked the Durable Object. It keeps judging week's data (and everything after) with no expiry, it needs one secret instead of a Cloudflare API token, it runs with the same tools as the existing relay, and every part of it was tested locally before the deploy. It is a new class, apart from the `Limiter`, which deletes everything at each new UTC day. Analytics Engine would also hold judging week, but its SQL API is sampled and limited, and its write path can't be tested before a deploy.

Sources: [Analytics Engine pricing](https://developers.cloudflare.com/analytics/analytics-engine/pricing/), [Analytics Engine limits](https://developers.cloudflare.com/analytics/analytics-engine/limits/), [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/).

### Choices made while building it

- **Test events are counted apart** from real ones for the event limit (`test:` in the count's key), the way free calls are counted apart from real ones. So a test run never uses up a real player's 500, and real play never blocks a test.
- **Every field is optional.** The allow-list refuses extra fields, wrong types and over-long strings, but a missing field is fine, so T68 can send what it has.
- **`player` may be upper-case hex** (Unreal's `New Guid` to string gives upper case). The relay stores it lower case.
- **`GET /stats` gives raw events a page at a time** (5,000 at most), not totals. The report adds them up, so a new heading needs no relay change and no deploy. The address hash is stored but never read back out.
- **`STATS_KEY` must be 16 characters or more**, or `/stats` acts as if it had none. The key is compared as SHA-256 digests with `crypto.subtle.timingSafeEqual`.
- **`analytics_report.py --new-key`** writes `Local/stats.json` with a fresh 64-character key and prints none, so the key never shows in a terminal or chat.
- **The event-limit test runs only with `--events-limit <n>`.** The limit is per address per UTC day, so a test that trips it can run once a day. Against the live relay it needs the var `IP_DAILY_EVENTS` set low for the run (the README says how).

### Test script fixes found on the way

- **macOS bash 3.2 brace-expands a `"{…,…}"` body nested in `"$(post "…")"`** inside double quotes. It split each such body into pieces at its commas and sent the pieces as separate requests. The old bad-request tests passed on the Mac only because every piece is "not JSON", a `bad_request` too, so they never tested what they named. Bash 5 (Git Bash on Windows) parses them right. The tests now pass the body as a plain argument (`postx`, `evx`), and the event tests check the exact reason (`error.detail`), not just `bad_request`.
- **The script calls `python`, and a Mac has only `python3`.** It now uses whichever there is.
- **The six body-shape tests (streaming, `max_tokens`, model, image, tools) sent no `"free": true`,** so against a relay with no keys (a local one) they stopped at `provider_unavailable`. They now send the run's free flag, so they check the body in free mode too.
- **"free vote picks a name from options" failed** since T55: `free_mode.json` now finds the vote phase by "The Cut" in the ask, and the test asked "Vote.". The test now asks "The Cut: vote.".

### The deploy and the live checks

- **A secret or var takes effect only once a version with it is deployed.** The first live run found neither `STATS_KEY` nor `IP_DAILY_EVENTS` active a minute after they were added; both worked after my person deployed them again and checked that the newest version was **Active** under **Deployments**. If `/stats` answers `not_found` with the key from `Local/stats.json`, check that first, then check that the secret holds only the 64 characters (no quotes or spaces).
- **The first live run used up this address's test events for the day** (it counted 7 against the limit of 3 that wasn't live yet), so the rerun needed `IP_DAILY_EVENTS` = 20. To repeat the limit test on the same UTC day, pass a limit above the day's count of test events plus 4.
- **`Local/stats.json` was made on the Mac with `--new-key`.** Copy the same file to the PC to run the report there.
