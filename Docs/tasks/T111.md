## Task

- **Why:** my question on 2026-11-19, in T91's session: do we need a dev relay and a production relay, especially for analytics? Not now. The relay deploys from `main` with each release (T91), `wrangler dev` is the dev relay (`Relay/README.md`, "Run it locally"), and test events are marked and left out of the report (T67, T68). One gap is left: every build sends the same `build`, `"2026-11-15"` from `Content/NHOS/Data/llm.json`, so the stats can't tell one release from another, or a test build from a release.
- **What changes:** a build that `Tools/deploy_itch.py` makes reports its version label, `<commit date>-<short sha>`, the same label as its file on itch.io (for example `2026-11-20-10f8540`: 18 characters, and the relay takes up to 20). The editor and builds packaged by hand report `local`. The report can group and filter events by build.
- **Steps:**
  1. **Read first.** T68's file (what the game sends, and when), T67's (the relay's `/event` and `/stats`), T89's and T91's (the deploy script and the release), and T92's if it is done (the Mac path and its `codesign` gate). `BPC_Analytics.Init` already reads `build` from `llm.json` (`Graphs/BPC_Analytics/Init.txt`), so no Blueprint changes.
  2. **The stamp.** In `deploy_itch.py`, after the deploy worktree is at the commit and before packaging, write the version label into the worktree's own `Content/NHOS/Data/llm.json` (the `build` field only, keeping the file's form). The package step then stages it as a loose file on both platforms. Never edit the file inside a finished build: on a Mac it sits inside the signed `.app`, and a change there breaks the signature. The next run's `git reset --hard` drops the stamp, so the check after the checkout ("changes after the checkout") still passes. With `--build`, the script stamps nothing, and says so.
  3. **The default.** Set `build` in the repo's `llm.json` to `local`. `python Tools/check_prompts.py --offline` must still pass (it wants 1 to 20 characters).
  4. **A gate.** After packaging, read the staged `llm.json` back from the build. If its `build` isn't the label, stop before the secrets check, and push nothing.
  5. **The report.** In `Tools/analytics_report.py`: a builds table (players, shows and events per build, newest first) and `--build <label>` to report one build alone. Mark the releases: labels in the form `YYYY-MM-DD-<sha>` whose commit is on `main` (`git merge-base --is-ancestor`, when the script runs in the repo). Everything else (`local`, the old `2026-11-15`) is not a release.
  6. **Docs.** "Deploys to itch.io" in `Docs/Builds.md`, "Analytics events" in `Relay/README.md`, the docstrings of both scripts, and T68's line about `build` in `Tools/check_prompts.py`'s docstring.
- **Done when:**
  1. A dry run of `main` (`deploy_itch.py --dry-run`) leaves a build whose staged `llm.json` holds `"build": "<main's label>"`, and the deploy worktree is clean again after the next run's checkout.
  2. A copy of that build, with `{"analytics": "test", "mode": "free", "autoplay": true}` in its `Local/switches.json`, plays a free autoplay show to `SHOW END`. Its log's `NHOS: ANALYTICS player ...` line says `build=<label>`, and `python Tools/analytics_report.py --test --build <label>` lists that show. The copy is deleted afterwards.
  3. A game window on the repo folder logs `build=local`.
  4. `python Tools/check_prompts.py --offline` passes.
  5. No key is in git or in this chat.

## Findings

Part 1 (2026-11-20, PC, worktree session, no editor):

- **The stamp** (`stamp_build` in `Tools/deploy_itch.py`). After `prepare_worktree` and before packaging, the script writes the version label into `<deploy worktree>/Content/NHOS/Data/llm.json`. It changes the bytes of the one `"build": "..."` line and nothing else: the file is read and written as bytes, so its CRLF line endings (the worktree checks out with `core.autocrlf`) and a BOM, if one were there, stay. Before it writes, it parses the result and checks that it equals the old object with only the top-level `build` changed; a missing line, two lines, a nested `build` or a label over 20 characters stop the run. The label comes from `version_label()`, the same function that now gives butler its `--userversion`, so the two can't drift apart. In the deploy worktree, after the run, `git diff` shows the one line: `"build": "2026-11-15"` became `"build": "2026-11-20-10f8540"`.
- **The gate** (`staged_build`). After the strip (and the Mac re-sign, if any), the script finds the one file in the build whose path ends in `Content/NHOS/Data/llm.json` (Windows: `NoHumansOnSet_Windows/AIMegaJam2026/Content/NHOS/Data/llm.json`; a Mac build: inside the `.app`, under `Contents/UE/AIMegaJam2026/`) and reads `build`. It only reads, so the Mac app's signature is untouched. If the value isn't the label, the run stops before the secrets check. `DirectoriesToAlwaysStageAsNonUFS=(Path="NHOS/Data")` in `DefaultGame.ini` is what makes it a loose file.
- **`--build`.** Nothing is stamped, and the script says so. With `--commit`, the gate checks the build against that commit's label (so a re-push of a build made before T111, which reports `2026-11-15`, now stops: it would ship a wrong label). With no `--commit`, the version is `<date>-manual` and the script only says what the build reports, so the secrets test of T92 (`--build <copy> --dry-run`, a planted key) still stops at the secrets check.
- **Tests of the two functions** on copies, before the real run: the stamp keeps every other byte and all 164 CRLFs; a second stamp replaces the first; a 21-character label, a missing `build` line and a nested one are refused; a BOM stays; the gate finds the file in both the Windows and the Mac layout and ignores an `llm.json` at another path; a build with none is refused.
- **The report** (`Tools/analytics_report.py`). A "builds" table after "players": build, release, players, shows, events, first seen, last seen, newest first by the build's first event. Release is `yes` for a `YYYY-MM-DD-<sha>` label whose commit is an ancestor of `origin/main` (as last fetched; the script fetches nothing), `no` for any other label, and `?` when git can't tell (the script isn't in a clone, or the clone doesn't have the commit). `--build <label>` reports that build alone; a label with no events lists the builds that have some. Checked offline with made-up events through `main()`: `2026-11-20-10f8540` is `yes`, a `dev` commit (`4caba44`) `no`, an unknown sha `?`, `local`, `2026-11-15` and an empty build `no`.
